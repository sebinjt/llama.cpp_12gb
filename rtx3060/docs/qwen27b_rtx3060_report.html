Inference report · RTX 3060 12 GiB · PCIe Gen3 x16 · llama.cpp fork · 2026-10-22

Qwen3.8-27B on an RTX 3060

A 27-billion-parameter hybrid model on a single 12 GiB consumer card, at contexts up to 200K tokens, with output identical to plain greedy decoding. The two limits are VRAM and the PCIe link. This report covers what was changed in llama.cpp to work around them, what each change bought, and where it helps.

"Stock" means the official llama.cpp release binary (b11717) at its best settings for this card: DFlash d7, q4_0 KV kept in VRAM, and only as many FFN layers on the CPU as it takes to fit. Headline decode numbers are greedy runs on a code prompt with thinking off, which drafts very well (about 6 tokens per step). A real coding-agent session with the model's default xhigh thinking and sampling accepts about 3 tokens per step and averages 23-26 t/s (section 6b).

1 · The problem

12 GiB of VRAM, and a 13.3 GB/s link behind it

Qwen3.8-27B has 64 layers: 48 GDN (recurrent) layers with a fixed-size state, and 16 full-attention layers that keep a KV cache. At q4_0 for K and V, each attention layer stores 1,152 B per token, so the cache costs 18,432 B per token across all 16 layers.

With DFlash (or no speculation) the loader skips the 0.70 GiB MTP head in the model file, so the IQ3_XXS weights take 9.0 GiB of the card (9,228 MiB). The Windows display driver's CUDA context, the recurrent state and compute buffers take about 1.0 GiB, and the DFlash drafter plus speculative rollback state take another 0.68 GiB. What is left for the KV cache is about 1.3 GiB: enough for 64K tokens, not for 128K or 200K.

KV that doesn't fit has to live in host RAM and cross the PCIe link on every decode step, once per staged layer. At 200K one layer is 225 MiB, which is 17.7 ms per step at the measured 13.3 GB/s. The 200K configuration stages 13-14 of the 16 layers, so about 250 ms of a 282 ms step is the PCIe stream, and the GPU sits idle for about 76% of the step.

Stock llama.cpp's best answer is to keep the KV on the card and move FFN layers to the CPU until everything fits. That works, but every CPU FFN layer runs its matmul on six CPU cores, 65-90 ms per verify step each, where this fork copies the same 38 MiB tensor to the GPU in about 3 ms under compute. The official b11717 binary with DFlash d7 gets 43.2 t/s at 8K, 10.4 at 64K, 4.7 at 128K and 2.7 at 200K (section 4b). Host KV (--no-kv-offload) is slower still: 3.6 t/s at 48K.

The IQ3_S model (11.28 GiB) has a second wall: its weights alone don't leave room for the KV cache, the recurrent state and a drafter. The old setup ran 2-4 GDN layers on the CPU, at about 19 ms per token for each one.

2 · The approach

Stream only what each layer needs, and make every stream carry more tokens

  1. Stream KV, don't offload layers. Each staged layer's KV is copied into one of two device slots just before its attention runs, on side streams, so the copy hides behind other layers' compute.
  2. Make every MiB of VRAM count. Remove scratch buffers, shrink the rollback state, put the MTP head's cache in a window, place the output head on purpose. Each 144-225 MiB freed is one more resident KV layer, worth 17.7 ms per step at 200K.
  3. Make one step carry many tokens. A verify pass costs the same PCIe whether it checks 1 token or 8. A drafter that gets 4-6 tokens accepted per step divides the PCIe cost per token by 4-6. DFlash drafts a whole 8-token block in one ~10-15 ms call.
  4. Stay exact. Speculative output equals plain greedy output, token for token, at every context. Every speed flag is opt-in, and with all flags off the default path is unchanged.
  5. For IQ3_S, stream weights too. Single large weight tensors, spread through the model, stream through two 48 MiB slots and are prefetched inside the CUDA graph, instead of running layers on the CPU.

One decode step at 200K

Copies run on side streams with two slots, so layer n+1's KV arrives while layer n computes. One verify pass checks the drafter's whole block, so the same PCIe stream pays for about 6 tokens.

4c · KV quantisation

q4_0/q4_0 stays the default; q8 K is a quality option that is free at short context

What the higher quant buys. Next-token distributions compared with f16 KV over 32 positions at 8K (teacher-forced, top-20 support). All three agree with f16 on the top token at every position; the differences are in the probabilities. These shifts are likely one to two orders of magnitude below what typical 3-bit weight quants cost (not measured for this model), so q4_0/q4_0 is good enough. The test is short-context only; no long-context recall test was run.

The q8 slowdown was routing, not size. LLAMA_FA_VEC_QUANT_KV sends quantized KV through the vector kernel, which has a fast path only for q4_0, so q8 KV fell back to a slow generic kernel for verify and prefill. Why q8 gets expensive at depth. Staged KV crosses PCIe on every step, and q8 K is 44% more of it. The MMA route also converts the whole K and V tensors to f16 on each call, and the memory pool keeps that buffer: 538 MiB at 128K, which is why 128K fits only with weights streamed. q8_0/q8_0 at 32K with 10 of 16 layers staged runs at the same speed as q4_0/q4_0 at the same setup (19.80 vs 19.66 t/s). Converting only the band the kernel reads would cut the buffer to about 8 MiB; it is scoped, not built. A q8 or q5 split-K decode kernel was not built either: q4_0/q4_0 is the production KV.

How the estimate works

VRAM. KV capacity = VRAM - weights on the GPU - driver/runtime reserve - drafter overhead. Weights on the GPU are the model file minus the MTP head, plus the head only in MTP mode: the loader skips it otherwise (9,228 vs 9,949 MiB for IQ3_XXS, 10,828 MiB for IQ3_S in DFlash runs). DFlash adds its drafter weights plus 163 MiB of rollback state.

Placement. Either all 16 KV layers stay resident, or r of them do, plus two staging slots, and 16 - r are staged. Weights are streamed only when nothing else fits, through two 48 MiB slots, up to the streamable limit. The placement with the shortest step is used.

Step. compute = trunk weight read time x k (2.28 for an exact 8-column verify, 1.93 for an exact 1-token step) + attention per 1K tokens of context + draft time + host time. PCIe = (staged KV + streamed weights) / link rate, with the link rate capped at host DRAM bandwidth / 1.4. A fraction of the compute (overlap) hides copies: step = compute + PCIe - min(overlap x GPU compute, PCIe). Decode t/s = accepted tokens per step / step.

KV pairs. Only q4_0/q4_0 has the dedicated split-K decode kernel. Q8 pairs run the generic vector kernel, whose attention cost per 1K tokens was measured for q8_0/q4_0 (2.0 ms verify, 0.76 ms at n=1) and is assumed for q8_0/q8_0 (2.4 / 0.9). Those two are rough. q5_0/q4_0 (5.5-bit K, 11% more KV bytes than q4_0/q4_0) also runs the vector kernel; its constants are fitted to the measured IQ3_XXS points at 8K, 32K and 64K (MTP d4 and no speculation): 3.6 ms verify, 0.47 ms at n=1, prefill quadratic term +2.15e-7, all within 2% of the measurements. Those were measured with LLAMA_FA_VEC_QUANT_KV set, which forces every q5/q8 verify and prefill batch through the vector kernel. Report 60.1 found that unsetting it moves q8_0/q4_0 verify onto the MMA kernel at near q4 cost (+1.6 ms/step at 8K, +8 ms at 32K, prefill unchanged); that route is the default here (0.50 ms per 1K verify for q8_0/q4_0, fitted; 0.45 for q5_0/q4_0 and 0.55 for q8_0/q8_0, assumed). Pick the old route in the parameters to see the vector-kernel curves. That route has one memory cost: it converts the whole K and V tensors to f16 on every call and the allocation stays in the pool, so it needs 4 KiB per token of context on top of the KV (256 MiB at 64K, 512 MiB at 128K). The estimator subtracts that from KV capacity. Measured at depth (report 60.6): q8_0/q4_0 costs -11% at 64K and -32% at 128K against q4_0/q4_0 at the same placement, and at 128K it fits only with 513 MiB of weights streamed. Converting only the band the kernel reads would remove the scratch; it is scoped, not built.

Prefill. T(n) = 1.756 ms x n + 6.70e-9 s x n² at 31 effective TFLOPS (the fit to the measured resident curve), scaled by the ubatch efficiency, plus 7.4% (DFlash) or 8.6% (MTP) for feature extraction, plus the per-ubatch copies of streamed weights and of the staged layers' prefix, of which 35% overlap compute. Q8 pairs add the vector kernel's attention term (measured for q8_0/q4_0 at 8K); q5_0/q4_0 adds its own, fitted at 8K-64K.

The step time is what the benchmarks measured; the acceptance is not. Decode steps took 108-112 ms at 7K context and 124-130 ms at 56-69K, matching the benchmark step times (110 ms at 8K, 114 ms at 64K with all KV on the card; the extra 10% at 64K is the 96K headroom, 6 of 16 KV layers staged). What changes is how many drafted tokens are accepted: about 3 per step instead of 6, because thinking text and sampled output are hard to predict.

Speed climbs as the reply moves from thinking to code. The first half of each reply, mostly thinking, ran at 21-23 t/s with either drafter; the last quarter, mostly code, ran at 32-34 t/s.

MTP is no better on thinking. Both drafters accept about the same per step during thinking. MTP accepts a larger share of its drafts (48% vs 29%) but drafts 4 tokens instead of 7 and spends 19 ms drafting against 10 ms, so DFlash stays about 5% ahead overall.

The levers are on the client. Temperature 0 and a lower reasoning effort (medium or low) raise acceptance; the server configuration is already at its measured step time. This model's chat template accepts only xhigh, medium and low; a client that sends high gets an HTTP 500.

One cache miss per conversation. The agent's second turn re-prefilled the whole conversation (35-42K tokens, about 2 minutes): the history it resent no longer matched the cached prefix, most likely because the previous reply's thinking was dropped. Every later turn reused the cache and prefilled only its new text.

Logs: results\rw\srv_96k_9931.log, srv_96k_9931_b.log, srv_96k_9931_mtp.log. One prompt with sampling, so the two drafters produced different texts of different lengths; treat the 5% as indicative.

7 · Method

Exactness and how the numbers were taken

Exact output. With the recommended configuration, speculative decoding (MTP or DFlash, any draft length) produces the same tokens as plain greedy decoding at 8K, 64K, 128K and 200K. Three things had to change for that: the decode-attention split partition (same for verify and decode at one position), the matmul warp count for 5-8 columns, and one matmul route (MMQ) for every batch width.

Several prompts, step time first. A change that alters the matmul route changes the generated text after the first divergence, and the text's draftability then moves t/s by ±15%. Mode decisions were made over five task prompts and judged on milliseconds per step, with accepted tokens per step reported beside it.

One GPU user at a time. Timed runs held a shared GPU lock, and runs that overlapped another job were discarded and repeated.

Weights untouched. No smaller weight quantisation was used anywhere. Numerical shortcuts stay opt-in and gated on a KL-divergence check.

Open items

  • int8 tensor-core prefill: 2.0-2.1x the MMQ matmul in isolation, accuracy gate passed (1.06x MMQ's own error). Paused.
  • A fresh 200K prefill with the current DFlash + budget setup measured 22 t/s, against 205 t/s for the older MTP setup and 265 t/s for the offline two-group path. Not yet explained.
  • Tree drafting at 200K: estimated +3-7%, needs multi-sequence batching.
  • q8 KV at 128K without weight streaming: convert only the KV band the attention kernel reads to f16 (about 8 MiB instead of 538 MiB). Scoped, not built.
  • A 200K server prefills short prompts 15.8% slower than a short-context server. A second, short-context server avoids it.
